## 1. Verdict in one paragraph

**There is one lesson worth acting on now, two worth scheduling, and one correction to the plan's own assumptions.** The lesson worth acting on now is a *doctrine*, not a feature: IngeTrazo never commits a solid it cannot prove is closed, and when it refuses it says so in plain words to the user (`CommandRejected`, `tools/pushpull.py:1910`). BIMWorks has the plumbing for exactly this — `failureMessage()`/`describeApiError()` already put engine reasons in the status bar (`src/store/useBimStore.ts:49-53`) — but the generic edit path has nothing to refuse with: `ElementUpdate` takes an untyped `Dict[str, Any]` (`backend/command_bus.py:116-118`), `update_element` applies whichever keys it recognises and **silently ignores the rest while still reporting `"updated"`** (`backend/ifc_service.py:2303-2417`), and an invalid footprint polygon degrades to a fan triangulation (`backend/ifc_service.py:2188-2211`). Second, IngeTrazo creates faces from drawn strokes with a DCEL planar arrangement that is *exact* for crossings, T-junctions, doubled lines, spurs and holes (`core/arrangement.py`); BIMWorks' footprint tracer is a greedy `candidates[0]` chain walk (`backend/sketch_model.py:223-287`), and running it shows the failure is worse than a missing feature — **an open boundary passes validation outright and has its closing edge invented** (§4.2, `probe-sketch-validation.py`). Third, and against expectation: **IngeTrazo has not solved incremental undo either.** It snapshots before every command and caps the stack at 200 steps precisely because of the memory cost (`core/history.py:156-166`, its issue #56). Its transferable contribution to BIMWorks' Phase 2 is a *bound*, a *refusal channel*, and the observation that a snapshot can preserve object identity instead of serialising the model — not an episode model.

## 2. What IngeTrazo actually is (facts, not impressions)

| Property | IngeTrazo |
|---|---|
| Intent | Freeform 3D modeller for AEC — "draw as if by hand" — with an **optional BIM tagging layer** on top (`README.md`) |
| Object model | A **shared-vertex, non-manifold polygon mesh** (`core/mesh.py`), not B-Rep: `Vertex`/`Edge`/`Face` with `__slots__`; `Edge.faces` is a *radial* list — "0, 1, 2, or more. More than two is non-manifold and fully supported (it is the common case in architecture)" (`core/mesh.py:86-99`); a `Face` stores its outer loop plus hole loops and no triangulation (`:178-207,277-284`). Coincident positions weld to one vertex by integer grid key at 1e-4 (`:49-57,340-351`). `core/geometry.py:16-50` is a *legacy value type* used only by the planner's throwaway simulation (`docs/halfedge-migration-plan.md:139-143`). **No persistent per-face or per-edge IDs** |
| Creation pipeline | Tool → *pure planner* (`core/topology.py`) → reversible command list → `History.execute` (`core/edits.py:1-23,49-80`) |
| Face creation | **DCEL planar arrangement**: split at intersections, snap to a quantised grid, prune degree-1 spurs, sort half-edges by angle, take next-clockwise to trace minimal bounded faces, nest CW cycles as holes (`core/arrangement.py:1-25`) |
| Push/pull rebuild | Deterministic plane rebuild replacing a "fragile heal chain": gather plane edges → arrangement → classify each region by **volumetric parity ray-casting** (material on one side = boundary face; neither = phantom; both = interior) → union into loops with holes (`core/cap_rebuild.py:1-25`) |
| Commit guard | "BIM-grade refusal": a push on a *closed* solid must leave a closed solid, else restore and refuse (`tools/pushpull.py:1910-1947`); flat sheets are exempt because they legitimately open |
| Watertightness — **two different definitions** | The push guard uses `is_closed` = every edge borders **at least two** faces (`core/orient.py:468-475`). The BIM quantity layer and the diagnostic use **exactly two**: "VOLUME is reported only when the set is watertight on its own (every edge of the set bordered by exactly two faces of the set)" (`core/bim.py:19-22,91-113`), and 0 / 1 / >2 are diagnosed separately (`plugins/solid_inspector.py:20-33`). The guard is therefore **weaker than the quantity rule** |
| Undo | ~100 reversible `Command` classes with `do`/`undo` (`core/history.py:94-104,285-4521`), **but** `History.execute` snapshots the mesh first for fail-safe rollback (`core/history.py:176,190-196`) and caps history at `max_steps = 200`, user-settable (`core/history.py:156-166`) |
| Failure semantics | `CommandRejected` = a deliberate no-op that restores the scene and keeps its reason in `last_rejected` for the tool to display (`core/history.py:87-92`) |
| Tool lifecycle | `Tool(ABC)` with `on_click/on_hover/on_cancel/on_value/on_key`, plus `rubber_band_lines`, `guide_preview_lines`, `inference_guide_lines`, `status_clause` (`tools/base.py:402-566`); `AxisMagnet` and `PlaneLock` are the inference plane (`tools/base.py:38,75`) |
| AI surface | Same direction as BIMWorks: `core/ai_bridge.py`, `plugins/ai_assistant.py`, `scripts/ingetrazo_mcp.py` driving the command engine |

Two consequences. IngeTrazo is a **sibling in edit architecture and a foreigner in geometry** — it has no B-Rep, no IFC-as-model-of-record, and its "BIM layer" is tags on mesh faces, so it cannot teach BIMWorks anything about IFC or wall joins. But it has spent its complexity budget exactly where BIMWorks is now spending its own: *turning a user's stroke into valid, reversible, explained geometry*.

## 3. Where BIMWorks is already aligned (do not change these)

1. **Everything is a typed command.** BIMWorks' `COMMAND_REGISTRY` of 31 Pydantic commands with a JSON Schema export (`backend/command_bus.py:309-341,375-384`) is the same architecture as IngeTrazo's command objects, and it is *stricter on the wire*: BIMWorks validates types and ranges before dispatch (`backend/command_bus.py:391-392`), which IngeTrazo does not do at the history boundary.
2. **Origin tagging and a replay journal.** `origin: ui|ai|script|cli` per transaction plus an append-only journal (`backend/command_bus.py:659-669,782-788`) has no counterpart in IngeTrazo. This is ahead, and the AI driver depends on it (`backend/ai_driver.py:809-820`).
3. **Create-path validation already refuses, with actionable messages.** `add_wall` rejects a zero-length baseline (`backend/ifc_service.py:1366-1367`); `Sketch.validate()` returns a human-readable problem and `set_roof_sketch` raises it (`backend/sketch_model.py:295-306`, `backend/ifc_service.py:744-751`); `extractPolygonFromLines` names the gap in the client (`src/store/useBimStore.ts:383-406`). The doctrine "an engine reason reaches the user's eyes" is already written down (`src/store/useBimStore.ts:45-54`). **The gap in this review is the edit path, not the create path.**
4. **A delta protocol with a differential-equivalence gate** (`docs/DELTA-MEASUREMENT.md`, 21 checks plus four fault-injection controls) is a stronger verification story than IngeTrazo's per-command tests. Keep it.

## 4. The lessons, in the order I would act on them

### 4.1 Refuse invalid edits, and give the edit path a vocabulary to refuse with — *act now*

IngeTrazo's commit path has three properties BIMWorks' `ElementUpdate` lacks:

- **A named refusal.** `CommandRejected` is "a command declining to happen, on purpose: it has put the scene back the way it found it and says why in plain words" (`core/history.py:87-92`). `History.execute` handles it as a true no-op — nothing on the undo stack, nothing in the error log — and keeps the reason in `last_rejected` for the tool to show (`core/history.py:172-200`).
- **A geometric precondition, checked at commit.** `_mutate` captures the mesh (`tools/pushpull.py:1940`), applies the push, and if the mesh *was* closed and is now open (and not flat), restores it and sets `_refused` (`:1944-1947`). The user gets "Push refused: would break the solid (left it unchanged)" at a 6-second timeout *specifically so the no-op is not silent* (`:1829-1833`).
- **A no-op detector.** It also refuses when the rebuild digested the push back to the starting state — "geometrically a no-op… flag it so the commit tells the user instead of failing silently" (`tools/pushpull.py:1948-1954`).

Three caveats, because IngeTrazo's README oversells this. First, the guard uses the **weak** closure predicate (`is_closed` = every edge borders *at least two* faces, `core/orient.py:468-475`), while its own quantity layer requires *exactly* two (`core/bim.py:91-113`) — so a push can be accepted that leaves geometry whose volume the BIM layer will afterwards refuse to report. Second, the guard is **whole-mesh scoped**: `is_closed(mesh)` is evaluated over the entire mesh, so a mesh that holds a closed solid *plus* any open sheet never arms the guard at all — `_component_is_closed` exists (`tools/pushpull.py:137-158`) but is not used for the refusal test. Third, the refusal is not a dead end: the commit **binary-searches** for the largest push the guard still accepts (six halvings, `tools/pushpull.py:1862-1907`) rather than just failing. And the guard is *not* universal — the README's "guarantees hermetic solids" holds only in push/pull; fillet, bevel, booleans and move use their own narrower refusals, which is why `plugins/solid_inspector.py` exists.

Two smaller guards are worth copying alongside it. `MoveVerticesCommand` refuses a weld that would leave a *local* defect, judged by a named defect vocabulary — duplicate / overlapping / pinched / crossed / flat faces, zero-length edges — via `defects_near`/`new_defects` (`core/history.py:2274-2288`, `core/topology.py:1872-1891`). And the transactional entry point used by the Python console, the AI assistant and the MCP bridge **pops the undo entry when nothing changed**, so a no-op script leaves no empty undo step (`core/ai.py:383-429`) — directly applicable to BIMWorks' `ai_driver.py`.

BIMWorks' edit path, by contrast:

| Where | Behaviour today |
|---|---|
| `ElementUpdateParams.updates` | `Dict[str, Any]`, no schema, no per-property types (`backend/command_bus.py:116-118`) |
| `update_element` unknown keys | Ignored. The function applies known keys per IFC class and falls through (`backend/ifc_service.py:2320-2399`) — a typo in a property name is indistinguishable from success |
| Return value | Always `{"status": "updated", ...}` even if nothing changed (`backend/command_bus.py:572-575`, `backend/ifc_service.py:2401-2417`) |
| Degenerate polygon | `_triangulate_polygon_2d` silently falls back to a fan, `return [[0, i, i + 1] for i in range(1, n - 1)]` (`backend/ifc_service.py:2188-2211`). A self-intersecting footprint becomes *a* solid with wrong area and no complaint |
| Value sanity | No check that `thickness > 0`, that coordinates are finite, or that a roof pitch is in (0°, 90°) on the *edit* path |

**Transferable mechanism, concretely:** add a `CommandRejected`-equivalent — a distinct exception type in `backend/command_bus.py` that `execute_transaction` treats as a *non-error rollback* (restore `pre_state`, increment no revision, record no journal entry, return `{"status": "rejected", "reason": ...}`), plus a validation hook in `update_element` that runs before `mark_mesh_dirty`. The client already knows how to display a reason (`src/store/useBimStore.ts:49-71`), so this is nearly free on the UI side. Then replace the `ElementUpdate` bag with a discriminated union of typed edit commands (`WallSetThickness`, `SlabSetPolygon`, …) — BIMWorks' own `docs/SPECIFICATION-v0.2.md` pattern — so unknown-property typos become schema errors, which the bus *already* rejects correctly.

**And a watertightness analogue.** IngeTrazo's definition is one line of counting (every edge exactly 2 incident faces, `plugins/solid_inspector.py:20-33`). BIMWorks does not need mesh watertightness — its elements are parametric extrusions — but the same shape of check applies to its own invariants: a wall whose baseline is shorter than its thickness, a slab polygon with zero area or a self-intersection, a hosted opening wider than its host, a roof whose slope curves no longer bound the footprint. Each is currently accepted or silently degraded.

### 4.2 Create faces from drawn strokes with a planar arrangement, not a chain walk — *highest-value technical item*

BIMWorks' footprint tracer is a greedy endpoint-connectivity walk (`backend/sketch_model.py:223-271`): at each step it takes `candidates[0]`, the first unused curve touching the current point, and the footprint is then whichever loop has the largest |signed area| (`:273-287`). IngeTrazo solves the same problem deterministically with a DCEL planar arrangement (`core/arrangement.py`).

I **ran** BIMWorks' tracer rather than only reading it — `python3 scratch/probe_sketch_validation.py` (companion to this review; `backend/sketch_model.py` imports only `dataclasses` and `typing`, so it runs without numpy or ifcopenshell):

| Input | BIMWorks today (executed) | IngeTrazo |
|---|---|---|
| **Open 3-segment chain** — the closing edge never drawn | `is_closed() → True`, `validate() → None`, and `footprint()` is **identical to the closed triangle's**. The missing edge is silently inferred | No face is produced (`tests/test_arrangement.py:94-98`) |
| Two crossing segments | `validate()` refuses with a gap message — correct — but `footprint()` still returns a **self-intersecting** 6-point fallback: the crossing is never split | Split at the intersection, snapped to a quantised grid (`tests/test_arrangement.py:45-52`) |
| Spur of ≥ 3 segments | The **open** spur is reported as a second "closed" loop, so `closed_loops()` — whose docstring says it exists to tell a footprint from interior slope lines — cannot be trusted for chains of ≥ 3 segments | Pruned: degree-1 chains border no face (`tests/test_arrangement.py:78-84`) |
| Two rooms drawn as two loops | `footprint()` = the **largest loop only**; the second is dropped | Both are faces (`tests/test_arrangement.py:55-63`) |
| Inner loop (atrium, shaft) | Dropped, not nested | Nested as a **hole** of the enclosing face (`tests/test_arrangement.py:65-75`) |
| Doubled edge | Two coincident curves | Collapses to one (`tests/test_arrangement.py:87-91`) |

The first row is the serious one, and it is a *silent correctness* defect rather than a capability gap. `validate()` is the only gate on the sketch commit path: `set_roof_sketch` calls it and raises on a problem before using `footprint()` (`backend/ifc_service.py:644-649`), and `_edit_sketch` routes every sketch mutation from **both** editing skins through it (`:709-725`). Because it returns `None` for an open chain, a floor or roof whose boundary was never closed is committed with its closing edge invented — and nothing downstream can detect it, because the footprint is the same array. The client's `extractPolygonFromLines` gap check (`src/store/useBimStore.ts:401-406`) does catch this case, but it lives in one skin; P4's stated design is that the backend is authoritative and the two skins are equal (`backend/sketch_model.py:1-13`), and a direct-manipulation drag or an overlay replay reaches `set_roof_sketch` without passing through it.

IngeTrazo's implementation is ~390 lines (`core/arrangement.py`) behind a pure, testable signature (`planar_arrangement(segments, origin, normal) -> [(outer_loop, [hole_loops])]`), and it is already the shared input to two consumers: face creation (`core/edits.py`) and the push/pull plane rebuild (`core/cap_rebuild.py`). BIMWorks has the same two consumers — sketch footprints for slab/roof (`backend/sketch_model.py`) and wall-join side faces (`backend/ifc_service.py:2902-3055`, which computes joins by proximity, miter clipping and square-off heuristics rather than by an arrangement of the plane). I would **port the arrangement rather than reimplement it**: same licence, same language, and its test file doubles as the acceptance spec. One caveat borrowed from IngeTrazo's own roadmap: it does **not** enforce non-self-intersection either (`core/topology.py:1060` states a deep concavity "can self-intersect (not handled)"), so the arrangement is not a general validity oracle — it is an exact face finder.

The `cap_rebuild.py` idea worth stealing separately is *how it decides which regions are boundary faces*: parity ray-casting from a sample point just off each region, on both sides, so the answer is **independent of the order planes are rebuilt in** (`core/cap_rebuild.py:8-18`). BIMWorks' join recompute is order-sensitive and needed Phases 1.1/1.2 to scope and index it; a volumetric classification is a categorically more robust answer to the same question.

### 4.3 Make the preview the same code path as the commit — *scheduled*

IngeTrazo states the rule explicitly: the push/pull **live preview applies the same mutation each drag frame**, then reverts via its own snapshot, so "the forming solid renders exactly as it will commit — clean, already stitched — instead of flashing the pre-stitch seams" (`core/history.py:2893-2906`). Commit then re-uses the *already-applied* result via `SnapshotMutation.from_states(before, after)` (`core/history.py:2908-2918`), and `redo` restores the captured result rather than re-running a closure over tool state that has since been reset (`core/history.py:2906-2912`).

BIMWorks draws its preview in React/SVG from store state and its commit is a separate engine call. That divergence is not hypothetical: `PlanViewport2D.tsx:270-271` documents a preview that "had frozen" because the mouse-move handler gated its update on `activeTool !== 'select'`. The IngeTrazo rule — *one mutation function, called by preview and by commit* — removes a whole class of bug, and it is compatible with BIMWorks' architecture: the mutation would live in the engine and the viewport would render the engine's staged result.

### 4.4 Undo: bound it now, and change *what a snapshot is* before changing the model — *act now (the bound), then Phase 2*

`docs/REFACTOR-PLAN.md:359-367` describes Phase 2 as replacing BIMWorks' snapshot with "incremental or structurally-shared representation", citing Revit's episode model. IngeTrazo supplies three corrections to that plan's premises.

1. **The bound is the cheap win, and IngeTrazo needed it too.** IngeTrazo *also* snapshots before every command (`core/history.py:176` — `snapshot = self.scene.mesh.capture_state()`), and its answer to the memory cost is `max_steps: int = 200`, user-adjustable, with the comment that "on a big model the stack is where the memory goes (issue #56)" (`core/history.py:156-166`). BIMWorks' `undo_stack` is **unbounded** (`backend/command_bus.py:670-679` appends one entry holding `pre_state` *and* `post_state`, each containing the complete IFC STEP text from `self.model.to_string()` plus deep-copied metadata — `backend/ifc_service.py:397-445`). Two full model serialisations per edit, retained forever, is a larger and more certain cost than the per-edit latency Phase 1 attacked. A cap plus a preference is a one-day change, and it is worth doing before Phase 2 starts.
2. **Inverse commands alone did not save them — and the reason is instructive.** Every IngeTrazo command has a `do`/`undo` pair (about 100 concrete classes, `core/history.py:285-4521`), and it *still* snapshots, for two distinct reasons the BIMWorks plan conflates. `History.execute` snapshots for **failure atomicity** — any throw must restore the pre-state and leave nothing on the undo stack (`core/history.py:190-196`). Separately, whole families of edits are wrapped in snapshot commands (`SnapshotCompound`, `SnapshotMutation`, `MeshSnapshotCommand`, `StitchSolidCommand`) explicitly because "the per-command inverses don't compose into a clean whole — undoing them piecemeal leaves orphan split edges and stray vertices behind" (`core/history.py:3068-3076`). A tool that splits, welds and hole-punches across many objects is exactly that case. Split the two concerns in Phase 2: **undo** can be delta-based, **failure atomicity** needs either a pre-state or validation strong enough that failures cannot occur mid-mutation.
3. **The most transferable idea in this section: a snapshot need not be a serialisation.** IngeTrazo's `capture_state` copies the *structure* plus every mutable field while keeping **the same `Vertex`/`Edge`/`Face` objects**, so `restore_state` brings the exact objects back and "delta commands holding references stay valid" across an undo (`core/mesh.py:982-1007`, rationale at `core/history.py:3118-3122`). BIMWorks does the opposite: `snapshot_state()` serialises the whole model to STEP text and `restore_state()` **re-parses it** (`self.model = ifcopenshell.file.from_string(snap["ifc_text"])`, `backend/ifc_service.py:449`) then re-attaches every entity handle by GUID lookup (`:498-509`). Every IFC entity handle in the process is invalidated and rebuilt on every undo. There is an honest trade-off here and the review should not hide it: BIMWorks buys a *complete, serialisable, durable* state — the snapshot **is** the model of record, which is why the replay journal and the delta protocol can trust it — whereas IngeTrazo's snapshots are in-memory only and cannot be persisted or diffed. The Phase 2 question is therefore not "snapshot or delta" but **which of the two jobs each snapshot is doing**: durability/diffability (keep serialising, but only where the journal needs it) versus rollback of a live edit (capture fields, preserve identity, and pay O(change) rather than O(model)).

| | IngeTrazo `capture_state` | BIMWorks `snapshot_state` |
|---|---|---|
| Captures | object graph + mutable fields | `model.to_string()` — full IFC STEP text |
| Restores by | copying fields back onto the same objects | `file.from_string()` + `by_guid()` re-resolution |
| Handle validity across undo | preserved (delta commands keep working) | invalidated; every `meta["entity"]` re-resolved |
| Cost | proportional to the mesh | proportional to the whole model, twice per edit |
| Persistable / diffable | no | yes — and the journal depends on this |

A final detail worth copying: **redo restores the captured after-state rather than re-running the mutation** (`core/history.py:2927-2935`), because the closure "usually closes over tool state that is reset right after commit, so re-running it on redo would crash". BIMWorks' `redo()` already does this correctly via `post_state` (`backend/command_bus.py:756-780`) — it is one of the things the snapshot design buys, and it argues against a wholesale move to inverse commands.

### 4.5 An inference surface, not a grid — *scheduled, and the plan already knows*

BIMWorks snaps to a 0.25 ft grid plus a 0.5 ft endpoint tolerance (`src/components/drafting/PlanViewport2D.tsx:247-260`), and the code itself says this "replaces this blanket grid with a real SnapEngine (endpoint / midpoint / …)" — the intended work is already noted. IngeTrazo's version is a coherent little subsystem worth reading before writing that engine: `AxisMagnet` (axis inference that is magnetic, with an on-screen axis), `PlaneLock` (adopting and previewing a snapped drawing plane, with its own colour), and tool-level `inference_guide_lines()` / `guide_preview_lines()` / `rubber_band_lines()` hooks with a `status_clause()` for the status bar (`tools/base.py:38-334,402-566`). Two further details BIMWorks' tool layer lacks: `on_value(value)` for typed numeric entry *during* an operation, and a **retype window** — after commit, the last distance stays re-editable (`tools/pushpull.py:1815-1835`, `PushPullTool.last_distance`). BIMWorks has the seed of this in `TemporaryDimension` + `applyTemporaryDimensionChange` (`src/types/bim.ts:182-190`); IngeTrazo shows the full pattern.

### 4.6 Propagate semantics through geometry edits — *one idea, cheap; one idea to admire and avoid*

IngeTrazo attaches semantics to geometry that is about to be destroyed and rebuilt, so it has had to answer "what happens to a tag when the geometry underneath it changes?" — a question BIMWorks will meet as soon as edits stop being purely parametric.

- **New geometry extends an existing object.** When a push/pull starts from a face carrying an `ifc` tag, the new walls and cap **join that tag**: "thickening a tagged slab, or raising a wall from a rect the active class stamped, yields a fully tagged solid" (`tools/pushpull.py:1927-1945`). The stamp is applied to faces that hold a vertex the push created, so it costs the size of the change.
- **Tag as you draw, before the rebuild.** `scene.active_ifc` (`core/scene.py:165-168`) causes `AutoTagDrawnFacesCommand` to be inserted **before** the plane rebuild, so the rebuild *inherits* the tag region by region rather than the tag being applied to faces that then disappear (`core/edits.py:400-413`); a fresh object id is allocated per draw commit so each drawn wall becomes its own object (`core/history.py:1943-1972`).
- **An explicit "what survives churn" list.** `PAINT_KEYS = ("color", "mat", "texture", "opacity")` is the declared set of attributes that hand off between faces, "the material identity that survives the churn" — with a deliberate comment that `layer` and `ifc` are **not** in it, because "they travel by their own rules" (`core/mesh.py:140-146`). Writing that list down, rather than discovering it per inheritance site, is the cheap part worth copying.

**The mechanism underneath is the thing to understand before copying.** IngeTrazo has **no persistent face or edge identifiers** — a verified negative, stated in its own migration plan: geometry is Python objects compared by identity, and commands **resolve their targets by position at do-time** (a recorded vertex loop matched by grid key, `core/history.py:77-84`; moves keyed by `_key(p)` sets, `:2255-2262`). Attribute inheritance exists precisely *because* ids cannot survive a rebuild. It works, but the cost is visible: `next_object_id` allocates by scanning loose faces for `max + 1` (`core/bim.py:36-43`), so tagged *groups* get no id at all and cannot collide against loose objects; and its own docs call position-keyed resolution the engine's "structural ceiling" (`docs/halfedge-migration-plan.md:12-20`). **BIMWorks should take the inheritance *rules* and keep its GUIDs** — its element-GUID model is strictly better here, and both projects share the same unsolved problem (stable sub-entity naming across topology edits), so neither should be read as having the answer.

BIMWorks keeps `type_properties` and `ifc_class` per element (`src/types/bim.ts:11-32,56-77`), and operations that create new elements — `WallSplit` (`backend/ifc_service.py:1058`), `ElementCopy` (`:903`) — must decide the tag question ad hoc today. A spec sentence of the form "geometry derived from a tagged element inherits its class and type unless explicitly overridden" is worth writing before those paths multiply.

### 4.7 A fuzz gate over the edit path, phrased as invariants — *worth scheduling*

BIMWorks' delta-equivalence gate proves *client state matches engine state*; it does not prove the *geometry* stayed valid. IngeTrazo's strongest test is a fuzz gate with both halves: `tests/test_fuzz_engine.py` runs 1,000 seeded sequences of real operations over four scenarios and asserts invariants **after every commit** — no unwelded duplicate vertices, no orphan face-less edges, no near-zero-area faces, a mesh that was closed stays closed (or collapses flat), a closed mesh has positive signed volume and no face left to re-orient, and no unmerged coplanar seam the user did not draw (`:245-292`). Known gaps are pinned as `KNOWN_BAD` xfails rather than deleted (`:448-461`). The companion tests are equally quotable as a contract: a push that would crack a solid must leave closure, face count and signed volume unchanged to within 1e-9, while a *valid* push must **not** be refused (`tests/test_pushpull_ux.py:494-530`); undo of a draw leaves no orphan split edges or stray vertices and **redo reproduces rather than re-runs** (`tests/test_undo_clean.py:24-54`).

Translated to BIMWorks: a seeded sequence of `CommandBus` transactions over a model, asserting after each commit that every element's parameters remain physically sane (positive thickness, non-zero baseline, finite coordinates, footprint area > 0, hosted openings inside their host), that the element-GUID set changes only as the commands imply, and that the plan-slice revision advances only when it should. That is the natural sibling of `check-delta-equivalence.mjs` and it is the gate that would have caught defects §5.2 and §5.3 below.

## 5. Defects found in BIMWorks while reviewing (record, per `REFACTOR-PLAN.md` §7/§8)

These are outside this review's scope to fix; they are recorded because they sit directly on the create/edit path, and the first is a units lie of the kind Phase 0.3 was meant to end.

1. **Sketch validation messages report feet as metres and centimetres.** `src/store/useBimStore.ts:353` correctly states the internal unit — `const tol = 0.5; // 6in endpoint snap tolerance (internal unit: feet)` — and `PlanViewport2D.tsx:238` confirms the drawing scale is 38 px per **foot**. But the messages at `src/store/useBimStore.ts:386` (`(${currentEnd[0].toFixed(1)}m, …)`) and `:404` (`${(dist(...) * 100).toFixed(0)}cm`) label feet as metres and multiply by 100 for centimetres. A 6-inch gap (0.5 ft = 15.24 cm) is reported to the user as **"50cm"** — off by 3.28×. `backend/units.py:100-139` has `format_feet_inches()` for exactly this; the client string bypasses it.
2. **`ElementUpdate` cannot fail for an unknown property.** As tabulated in §4.1: an untyped `updates` dict, silent ignoring of unrecognised keys, and an unconditional `"updated"` status. Any AI- or script-originated edit (the `origin` field exists precisely to allow those) can therefore be a silent no-op while the journal records success.
3. **Invalid and *open* footprints are accepted as valid.** Two independent facts, the first executed: (a) an open 3-segment chain returns `is_closed() == True` and `validate() == None`, with a `footprint()` identical to the closed triangle's, so the only gate on the sketch commit path (`backend/ifc_service.py:644-649`, reached from both editing skins via `_edit_sketch`) passes a boundary that was never closed and the missing edge is inferred — reproduce with `python3 scratch/probe_sketch_validation.py`; (b) `_triangulate_polygon_2d` swallows a Shapely failure or an invalid polygon and returns a fan (`backend/ifc_service.py:2188-2211`), so a self-intersecting slab/roof polygon yields wrong area with no diagnostic. A spur of ≥3 segments additionally reports as a second "closed" loop, which defeats the boundary-vs-slope-line distinction `closed_loops()` exists to make.
4. **The undo stack is unbounded.** `backend/command_bus.py:670-679`, each entry retaining two full IFC serialisations (`backend/ifc_service.py:397-445`). §4.4.
5. **The refactor plan's own command-count invariant is stale, and it is a data-loss trap.** `docs/REFACTOR-PLAN.md:83` states `grep -c '^\s\{4\}"[A-Z]' backend/command_bus.py` should yield "**26 registry entries**", and §4 T2 repeats "`COMMAND_REGISTRY` must stay at **26** plus anything you add". The registry actually has **31** (`backend/command_bus.py:309-341`, counted directly), and the project's own `docs/DELTA-MEASUREMENT.md:94` says "All **31** registered commands maintained without regression". An agent obeying §2.3 literally would read a correct tree as broken — and T2's remedy for a *shrunk* count is the opposite of the remedy implied by an inflated expected count, so the plausible wrong action is deleting commands to hit 26. That is precisely the failure mode T2 exists to prevent. The expected value should be restated as "≥31" (or the count dropped from the gate), and the two documents reconciled.

## 6. What does **not** transfer

| IngeTrazo thing | Why not |
|---|---|
| The mesh-topology object model (`Edge`/`Face` with Python identity equality, `core/geometry.py:16-50`) | It is the *opposite* of BIMWorks' parametric element records. Identity is object identity within a session; it does not survive a save/load or a snapshot restore, which is why `History._rebind_dimensions` has to heuristically re-find vertices after topology changes (`core/history.py:212-215`). BIMWorks' GUID + parameters is the better model for IFC, quantities and schedules. **Borrow the arrangement, not the object model.** |
| Persistent sub-entity naming | IngeTrazo does not have it — a verified negative, stated in its own migration plan. Neither project solves stable face/edge naming across edits; do not expect a solution here. |
| **Position-keyed target resolution** (`_key` grid at 1e-4, `core/mesh.py:49-57`; `_find_face_by_loop`, `core/history.py:77-84`) | O(n) scan per command plus float-tolerance fragility. Its own docs call this the engine's "structural ceiling" (`docs/halfedge-migration-plan.md:12-20`). BIMWorks' GUID + parameter addressing is strictly better — take the inheritance rules, not the addressing. |
| One host-language object per vertex/edge/face | Its ROADMAP names this as a liability ("Each face is a Python object (about 3 KB)… the fix is **light components**", `ROADMAP.md:51`). A web/TS engine wants typed arrays and indices. |
| Whole-mesh validation as the per-commit gate | `is_closed`, `signed_volume` and `orient_outward` are O(mesh) per edit, and its ROADMAP wants "local orientation" instead. BIMWorks has just spent Phase 1 deleting O(model) work from the edit path (`REFACTOR-PLAN.md:111-121`); re-introducing a whole-model scan per edit would reverse it. |
| `manifold3d` for booleans (`core/solids.py:97-157`) | A C++/WASM kernel, not a TypeScript library. |
| The 4,605-line `core/history.py` with ~100 command classes, and a fixed 15-class IFC preset list (`core/bim.py:29-33`) | BIMWorks' schema-exported registry is the better shape: it is the AI driver's validation surface (`backend/ai_driver.py:809-820`). |
| The BIM layer | Tags on mesh faces with volume gated on watertightness (`core/bim.py:20,233`). BIMWorks' IFC-as-model-of-record is categorically stronger. |
| `Tool` / grip / work-plane classes (`tools/base.py`, PySide6) | Qt-specific UI machinery. Read the *interaction model*, not the code. |
| 200-step history as a *solution* | It is a mitigation with a known open issue (#56). Adopt the bound; do not adopt "snapshots are fine". |
| `SnapshotMutation`'s closure-over-tool-state design | It works around Qt tool object lifetimes (`core/history.py:2906-2912`); BIMWorks' commands are JSON and stateless by design, which is better. |

## 7. What this review could not settle

1. **Whether a bound on undo is enough for BIMWorks' stated budget.** I did not measure BIMWorks' snapshot cost; `scratch/_probe_snapshot_cost.py` exists in the pulled tree and appears to be exactly the right instrument. The recommendation in §4.4 is a bound, justified by IngeTrazo's identical mitigation — not a measured budget claim.
2. **Whether porting `core/arrangement.py` is a drop-in.** It is pure-Python geometry plus `QVector3D` from PySide6 (`core/geometry.py:12`), so porting means replacing the vector type. Its 390 lines are plausibly a day; its *tests* are the real work, and I did not run them.
3. **Whether BIMWorks' join engine should move to a volumetric classification.** `REFACTOR-PLAN.md:320-322` explicitly forbids touching the join engine in the current phase, and Phases 1.1/1.2 have just made it incremental and indexed. §4.2's `cap_rebuild` observation is recorded as a *direction*, not a work item.
4. **IngeTrazo's actual commit-time guard coverage.** I read the push/pull guard, the move-vertex local-defect check and the solid inspector; I did not enumerate every mutating tool to see which ones lack an equivalent precondition check. The README's claim that the engine "guarantees hermetic solids" is **not** supported by the code — the guard exists in push/pull, and `plugins/solid_inspector.py` exists precisely because bad solids still occur.
5. **How much the guard's whole-mesh scoping costs in practice.** I verified the predicate (`is_closed` over the whole mesh, `core/orient.py:468-475`) and that a per-component variant exists but is unused for the refusal test (`tools/pushpull.py:137-158`); whether that gap bites in real models is not something source reading settles.
6. **Any IngeTrazo test result.** Every test claim above is read from the test source, not executed — no IngeTrazo test was run. Its own documentation also drifts from its code in places (a ModernGL claim its viewport contradicts; a `core/history.py` header that says "not snapshots… only the delta" twelve lines above a comment that every command carries a mesh snapshot). Treat its code as the authority, as this review has.
