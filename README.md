# BIMWorks

**A native-IFC architectural BIM authoring application — AI-first by design.**

BIMWorks is an open-source (GPL-3.0) "Revit LT-class" desktop BIM app for architects: parametric
modeling (walls that join at corners, hosted doors and windows, datum-driven levels and grids),
Revit-muscle-memory UI (ribbon, two-letter hotkeys, Project Browser, Properties, view range, sheets),
and 100% vector construction documents — with a typed command bus that lets an AI agent drive the app
through the same interface as the ribbon.

| Decided | Value |
|---|---|
| Project file | `.bimworks` hybrid container: `model.ifc` (IFC4 ADD2 TC1, model of record) + `parametric.json` overlay (constraints, joins, sketches) |
| Schema | IFC4 ADD2 TC1 of record; IFC4.3-ready serializer boundary; reads IFC4x3 |
| Licence | GPL-3.0 |
| Internal units | Decimal feet (Revit-identical); metric at the IFC boundary |
| Engine | Python 3.13 + IfcOpenShell + planegcs **engine process** (`backend/`, port 8008) |
| Shell | React 19 + TypeScript + Three.js + dockview, built by Vite (`src/`, port 5173) |
| AI | Typed CommandBus (JSON Schema 2020-12) + in-app prompt bar — the LLM emits typed command programs, never GUI clicks |

## Running it

There are **two processes**. The browser app talks to the Python engine, and neither works alone — a
blank page is usually one of them missing.

### 1. Engine (Python + IfcOpenShell) — port 8008

From the repository root:

```bash
python -m venv .venv          # once
```

Then activate, install and run:

```bash
# Windows
.venv\Scripts\activate
pip install -r requirements.txt
python backend/main.py

# macOS / Linux
source .venv/bin/activate
pip install -r requirements.txt
python backend/main.py
```

Requires **Python 3.13**. Dependencies are declared in [`requirements.txt`](requirements.txt) —
FastAPI, Uvicorn, IfcOpenShell, shapely, PyMuPDF, planegcs and others. `python-multipart` is a hard
dependency for file upload and is declared, so a single `pip install -r requirements.txt` suffices.

Verify the engine before blaming the browser:

```bash
curl http://127.0.0.1:8008/health             # {"status":"ok",...}
curl http://127.0.0.1:8008/api/project        # JSON model summary
```

Interactive API docs are served at <http://127.0.0.1:8008/docs>.

### 2. Frontend — port 5173

```bash
npm install          # NOT `npm ci` across platforms — see below
npm run dev          # http://localhost:5173
```

[`vite.config.ts`](vite.config.ts) proxies `/api` to `127.0.0.1:8008`, so the engine must be running for
anything to load. For a production build use `npm run build` and serve `dist/`.

### If the page is blank

Run the diagnostic instead of guessing:

```bash
npm run diagnose        # node scripts/diagnose-blank-page.mjs
```

It checks the two causes seen so far and reports which applies.

**Cause 1 — no WebGL context.** The 3D viewport needs a GPU context, and headless, remote-desktop and
VM sessions frequently have none. This used to take the whole page down; an `ErrorBoundary` and a
fallback in `Viewport3D` now keep the rest of the UI usable and say so. On such a machine, expect the
3D view to be replaced by a message and use the 2D plan view.

**Cause 2 — `node_modules` copied between platforms.** `rolldown` and `lightningcss` ship **native**
binaries (`binding-linux-x64-gnu`, `lightningcss-linux-x64-gnu`). A `node_modules` copied from another
OS — or built on a different CPU — fails to load them and Vite never serves the app. **Always run
`npm install` on the machine you are running on; never copy `node_modules`.**

## Testing

### Gates — run these before committing

```bash
npm run check           # the five gates below, then tsc --noEmit
```

| Script | What it protects |
|---|---|
| `npm run check:bus` | That the UI store holds no independent model state |
| `npm run check:ui` | UI interaction invariants (a UI-P0 gate) |
| `npm run check:state` | The `GET /api/state` bundle's invariants |
| `npm run check:delta` | Delta-protocol equivalence |
| `npm run check:snap` | Snap candidate resolution, priority hierarchy and selection geometry |
| `tsc --noEmit` | Types |

The gates exist because the violations they catch were real and shipped. Do not weaken them.

> **The UI gate makes real HTTP calls to the engine.** Start the backend first, or the run is misread —
> the same trap recorded in `docs/REFACTOR-PLAN.md` §2.1.

### Engine regression suites

Run from the repository root, with the engine's Python:

```bash
python scratch/test_v2_core.py             # CommandBus, schemas, batches
python scratch/test_transactions.py        # undo/redo atomicity
python scratch/test_wall_joins.py          # join geometry (see caveat below)
python scratch/test_wall_joins_matrix.py   # join fixture matrix + meta-test
python scratch/test_container_fidelity.py  # .bimworks round-trip fidelity
python scratch/test_dependency_graph.py    # recompute graph, constraint solver
python scratch/test_hlr.py                 # 2D hidden-line pipeline
python scratch/test_sketch_model.py        # sketch data model
python scratch/test_bus_parity_audit.py    # bus parity, audit form
```

There are 29 `test_*.py` suites under [`scratch/`](scratch/); the nine above are the ones most often
reached for, and the remainder cover imports, hosted openings, roof updates, mesh HLR, HTTP container
round-trips, units boundaries, scale gating, trim/split, and the type layer.

### Why there are two join suites

**Both suites now run anywhere.** `test_wall_joins.py` used to print a Unicode check mark and die with
`UnicodeEncodeError` under `cp1252` before completing a single check, so its "18 checks passing" was a
property of the terminal rather than of the code. Its output is ASCII now and it reports 18/18 with no
environment variable set.

**`test_wall_joins_matrix.py` is the suite that can actually fail.** Its sibling passed 18/18 with
every fixture wall at `thickness: 0.3` — the single case where an angle-bisector miter and a side-face
miter agree — so it stayed green through a miter error of **0.4 ft on a 9:1 thickness pair**. The
matrix suite varies thickness, join angle, walls at the junction, join mode and end state, and carries
a meta-test asserting that variation. Both suites pass today (18 and 37 checks).

That is the rule it exists to enforce: **if a key parameter is constant across a corpus, the suite is
blind on that dimension regardless of how many checks it has.** It applies to probes as well as tests.

## Key design decisions

Each is recorded with its rationale in [`docs/SPEC.md`](docs/SPEC.md) §11 and stated normatively in
[`docs/SPECIFICATION-v0.2.md`](docs/SPECIFICATION-v0.2.md).

- **Hybrid container.** IFC has no recompute semantics, and property sets are static data rather than a
  constraint system. So `model.ifc` stays a valid, standalone, third-party-readable IFC4 file, and a
  `parametric.json` overlay carries what IFC cannot express — constraints, join policies, sketches,
  view state. Discarding the overlay must degrade the model to *static but valid*, never to corrupt.
- **Decimal feet internally**, converted to metres at the STEP boundary and nowhere else.
- **`edit_object_placement` must be called with `is_si=False`**, because BIMWorks' values are already in
  the file's unit. Getting this wrong produced a 3.28× placement error and once silently disabled
  opening subtraction.
- **GPL-3.0**, chosen partly because it unlocks **planegcs** (FreeCAD's PlaneGCS) as an embedded
  constraint solver rather than a hand-rolled one.
- **The bus is the interface.** Every mutation is a typed, journaled, undoable transaction with a
  declared origin (`ui`, `ai`, `import`). The UI is a skin over the bus, and a parity gate proves it.
- **Sheets are a first-class subsystem, not a print dialog.** A view is a document object that can exist
  unplaced; placement is a separate object referencing both sheet and view. IFC has no view, sheet,
  viewport, marker or template model, so all of it lives in the overlay.
